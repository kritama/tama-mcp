# Solution 03 — fix the inferred code paths and keep the runtime contract honest

Date: 2026-09-11

Applies to: `wip/tama-mcp-specification/problems-03.md`

## Decision

The two remaining warnings are reproducible and neither requires a Dialyzer
suppression.

1. `Tool.field/2` needs its own `no_return()` contract because it is a function
   generated by the default argument. A contract for `field/3` alone does not
   cover it. Prefer deleting the runtime misuse guard because the schema macro
   parses `field` calls as AST and does not import this function. If the custom
   diagnostic is retained, specify both arities explicitly.
2. The `runtime.ex:1` warning comes from the redundant `is_atom/1` and
   `not is_nil/1` checks in `validate_server!/1` and
   `validate_authorization!/1`. `fetch_module!/2` has already narrowed both
   inputs to non-nil atoms. Remove the repeated checks and retain the loaded
   module/export checks.
3. Do not treat weakening `Runtime.t()` as the complete fix. Keep `module()` for
   the two required, validated modules and finish the Phase 1 configuration
   boundary by validating supported values and removing future-phase options.

The small warning-only change was verified in an isolated copy: removing the
redundant module guards, adding `no_return()` specs for both `field/2` and
`field/3`, and retaining `module()` for `server` and `authorization` makes
`mix dialyzer --no-check` report zero errors and zero skipped warnings.

## Item A — `field/2` needs an arity-2 contract

The proposed single contract in `problems-03.md` is insufficient:

```elixir
@spec field(atom(), term(), keyword()) :: no_return()
def field(_name, _type, _opts \\ []) do
  raise CompileError, description: "..."
end
```

Elixir generates a separate `field/2` wrapper for the default argument. In the
isolated check, adding only the contract above left this warning unchanged:

```text
Function field/2 has no local return.
```

Adding contracts for both arities removed it:

```elixir
@spec field(atom(), term()) :: no_return()
@spec field(atom(), term(), keyword()) :: no_return()
def field(_name, _type, _opts \\ []) do
  raise CompileError,
    description: "field/3 must be called inside an input_schema/2 or output_schema/2 block"
end
```

However, the cleaner design remains the one in `review-01.md`: remove this
function. `use TamaMCP.Tool` does not import `field/2` or `field/3`, and
`input_schema`/`output_schema` consume the inner calls as syntax. The function
therefore exists only as a public runtime entry point that always raises. An
out-of-context call can fail as an undefined DSL form without carrying a
runtime function solely for a custom message.

If the custom diagnostic is considered part of the developer experience, keep
it and use both specs. Do not restore `@dialyzer`.

## Item B — the `runtime.ex:1` warning is localized

Running the raw formatter produces:

```text
{:warn_matching,
 {~c"lib/tama_mcp/transport/streamable_http/runtime.ex", 1},
 {:pattern_match, [~c"pattern 'false'", ~c"'true'"]}}
```

There is no function or more precise source location in the warning tuple.
Dialyzer's `error_location` setting can select line or column presentation, but
it cannot reconstruct a location that the BEAM annotation does not contain.
`mix dialyzer --format raw` is therefore the end of the available location
information for this warning. Source reduction or bisection is the appropriate
localization technique here.

The bisection result is conclusive. `fetch_module!/2` returns only a non-nil
atom:

```elixir
value when is_atom(value) and not is_nil(value) -> value
```

Consequently, these prefixes are always true at their call sites:

```elixir
is_atom(server) and not is_nil(server)
is_atom(authorization) and not is_nil(authorization)
```

Elixir's strict boolean `and` chain is lowered into branching code. Dialyzer
can prove that the generated `false` branch for those already-established
predicates is unreachable, even though the later `Code.ensure_loaded?/1` and
`function_exported?/3` checks can still return false. That is why the warning
says `false` cannot match `true` rather than saying that the entire validator
condition is always true.

Remove only the redundant predicates:

```elixir
defp validate_server!(server) do
  unless Code.ensure_loaded?(server) and
           function_exported?(server, :tools, 0) and
           function_exported?(server, :name, 0) and
           function_exported?(server, :version, 0) and
           function_exported?(server, :tool, 1) do
    raise ArgumentError,
          "server: #{inspect(server)} is not a compiled TamaMCP server " <>
            "(define it with `use TamaMCP.Server`)"
  end
end

defp validate_authorization!(authorization) do
  unless Code.ensure_loaded?(authorization) and
           function_exported?(authorization, :authenticate, 2) do
    raise ArgumentError,
          "authorization: #{inspect(authorization)} does not implement " <>
            "TamaMCP.Authorization (missing authenticate/2)"
  end
end
```

Do not weaken `fetch_module!/2` to make the downstream checks uncertain again.
That would silence a useful inference instead of removing duplicated work.

As a later DRY improvement, the required export check can be owned by one small
helper that returns the validated module. Preserve the server- and
authorization-specific error messages; do not replace them with an opaque
generic failure.

## Keep `module()` for validated module fields

The following explanation in the current source is misleading:

```text
Dialyzer cannot prove a term read from Plug init options to be module().
```

It is true only for values copied directly from `Keyword.get/3`. It is not true
for `server` and `authorization` after `fetch_module!/2`. Restoring these fields
to `module()` still passes Dialyzer after the redundant guards are removed:

```elixir
server: module(),
authorization: module(),
```

Although Elixir's built-in `module()` type is represented by an atom, it
communicates the runtime's intent better than `atom()`. The required modules
are also checked for loading and required exports, so their type should not be
downgraded merely because the original input was a keyword value.

The other changes require separate judgment:

- `String.t()` and `binary()` are equivalent at the type level, but
  `String.t()` better communicates that `context_headers` contains header-name
  strings.
- The safe metadata callback cannot honestly promise a map result solely from
  an arity guard. Either type its untrusted return as `term()` and validate the
  returned value at the invocation boundary, or wrap it in a function whose
  return is normalized to a map. Do not claim a map return without enforcing
  it.
- Optional adapter values copied directly with `Keyword.get/3` are still
  unconstrained terms. Changing their fields to `atom() | nil` makes the
  contract closer to the currently inferred success type, but does not make
  invalid configuration safe or usable.

## Complete the Phase 1 configuration boundary

The type edits in `problems-03.md` remove the two `invalid_contract` warnings,
but they do not resolve the underlying finding from `review-01.md`:
`Runtime.build/1` still accepts settings it neither validates nor uses.

For the current Phase 1 implementation, prefer a smaller runtime containing
only:

- `server`;
- `authorization` and `authorization_options`;
- Phase 1 limits that are actually enforced;
- `telemetry_prefix` and `safe_metadata`; and
- `context_headers`.

Remove `clock`, `identifier`, `task_store`, `task_store_options`, `task_runner`,
`task_runner_options`, `notification_bus`, and `notification_bus_options` until
their Phase 2 or Phase 3 behaviours and call paths are introduced. Reject
unknown top-level options so a misspelling or premature future option cannot
appear to initialize successfully.

This also means `validate_tool_policies!/2` must not accept a non-nil placeholder
`task_runner`. Phase 1 has no task-runner behaviour or durable path. Reject a
server containing a `task: :required` tool during initialization; introduce
the option only when Phase 2 can honor it.

Every retained option should be read through a helper that returns its
validated, normalized value. For example:

```elixir
authorization_options =
  opts
  |> Keyword.get(:authorization_options, [])
  |> validate_keyword!(:authorization_options)

telemetry_prefix =
  opts
  |> Keyword.get(:telemetry_prefix, [:tama_mcp])
  |> validate_telemetry_prefix!()

context_headers =
  opts
  |> Keyword.get(:context_headers, [])
  |> validate_context_headers!()
```

The return values, not the original `Keyword.get/3` terms, must be inserted into
the struct. This is the boundary design Dialyzer can verify and callers can
rely on.

If the implementer elects to retain future-phase options despite the phase
plan, each module must instead have a defined behaviour/export contract,
non-nil modules must be loaded and checked, each associated options value must
be a keyword list, and tests must prove the validation. Merely typing the raw
values as atoms is not an acceptable substitute.

## Counter explanation

`Total errors: 3, Skipped: 1` does not indicate an undisclosed source warning
or an inline suppression.

Dialyxir counts the warning list before formatting, formats it, and then calls
`Enum.uniq/1`. A direct call to the underlying Dialyzer API confirms that the
current analysis returns the `runtime.ex:1` `warn_matching` tuple twice. The
formatter collapses that exact duplicate and reports the difference as
`Skipped: 1`. That is why only these two unique raw tuples are printed:

```text
{:warn_return_no_exit, ..., {:no_return, [:only_normal, :field, 2]}}
{:warn_matching, ..., {:pattern_match, ...}}
```

There is no `.dialyzer_ignore.exs`, configured ignore file, or remaining
`@dialyzer` involved in that count. Once the two actual causes are fixed, the
verified output is `Total errors: 0, Skipped: 0`.

Dialyxir documents the raw formatter as the pre-pretty-print representation:
[Dialyxir command-line formats](https://dialyxir.hexdocs.pm/readme.html#command-line-options).
Erlang documents `error_location` as choosing line versus column locations,
not as a source-localization mode:
[Dialyzer options](https://www.erlang.org/doc/apps/dialyzer/dialyzer.html).

## Required tests

Add or retain focused tests for the actual configuration boundary:

- valid server and authorization modules build successfully;
- `nil`, non-atoms, unloaded module atoms, and modules missing required exports
  fail with bounded `ArgumentError` messages;
- non-keyword `authorization_options` are rejected;
- invalid telemetry prefixes and context headers are rejected;
- unknown top-level runtime options are rejected;
- Phase 2/3 adapter options are rejected while they are unsupported;
- a Phase 1 server containing a task-required tool is rejected regardless of a
  placeholder `task_runner` value; and
- if the `field` misuse guard is retained, tests cover both arities and their
  diagnostic.

Do not write tests that merely assert the struct accepts arbitrary terms. The
tests should prove that successful construction establishes every invariant
claimed by `Runtime.t()`.

## Acceptance criteria

Problem 03 is closed only when:

- there are no source-level Dialyzer suppressions or ignore files;
- `field/2` is removed, or both always-raising arities have explicit
  `no_return()` contracts;
- module validation has one atom/non-nil boundary and no redundant downstream
  guards;
- validated required modules retain the semantic `module()` type;
- successful `Runtime.build/1` establishes every invariant in `Runtime.t()`;
- unsupported future-phase settings are removed or completely validated;
- Phase 1 cannot pretend to support required-task execution through a
  placeholder atom;
- focused runtime validation tests pass; and
- `mix dialyzer --no-check` reports zero errors and zero skipped warnings.
